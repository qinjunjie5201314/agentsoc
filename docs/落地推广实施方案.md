# AgentSoc 落地推广实施方案

> 定位：内部工具 · 目标用户：企业安全/合规团队 · 资源：单人
> 现状：MVP 已跑通 L1-L4 纵深防御全链路（16/20 任务完成，469 测试通过）
> 文档日期：2026-09-10

---

## 0. 一句话结论

当前产品是「**能跑通的技术 demo**」，距离「**安全/合规团队愿意采纳的内部工具**」之间，
缺的不是更多检测规则，而是三件事：**工程化（能稳定跑）**、**合规性（能对上审计要求）**、
**真实接入（证明对真实 Agent 有效）**。下面按这三个缺口拆成可执行的阶段。

---

## 1. 差距分析（MVP → 可落地）

| 维度 | 当前状态 | 安全/合规团队的期望 | 差距 |
|---|---|---|---|
| 检测能力 | L1-L4 全链路，13 条内置规则 + mock 判别 | 低误报、可调优、可解释 | 判别模型是 mock，需换真实模型 |
| 审计 | 三表 + 查询端点 | 出报表、可导出、可归档、可签名 | 无报表、无导出、无留存策略 |
| 策略 | YAML 热更新 + NL 转策略 | 可审批、可回滚、有变更审计 | 有 fail-safe 但无审批流、无变更台账 |
| 部署 | 单机 uvicorn + SQLite | 私有化、容器化、可监控 | 无 Docker 编排、无日志采集、无监控 |
| 接入 | OpenAI/Anthropic 双协议 proxy | 无感接入真实 Agent + 低延迟 | 未对真实 Agent 做端到端验证 |
| 安全自证 | 无 | 自身安全（密钥、注入、越权） | 无安全加固、无威胁建模 |

**核心洞察**：安全/合规团队买的是「**责任可转移 + 可审计**」，不是「更多检测规则」。
落地路线的重心必须放在"让每一次拦截都有据可查、每一次策略变更都可追溯"上。

## 2. 分阶段路线图（4 个阶段）

### 阶段 0：补齐 MVP（1-2 天，纯内部工作）

把剩余 5 个任务做完，让产品完整：

| 任务 | 内容 | 产出 |
|---|---|---|
| D2 | CLI 日志展示（Rich 实时风险事件流） | `app/cli/dashboard.py` |
| D3 | 会话重放 timeline | `app/audit/replay.py` |
| E1 | 30+ 攻击样例集（OWASP LLM Top 10 覆盖） | `tests/fixtures/attacks/` |
| E2 | 真实 Agent 接入演练 | `examples/*.md` |
| E3 | README + Quickstart | `README.md` |

**验收**：产品完整，能对外演示完整攻击→拦截→审计闭环。

### 阶段 1：工程化（1-2 周，单人主力）

目标：从"能跑"到"能稳定跑、能被别人部署"。

1. **真实判别模型替换 mock**（1-2 天）
   - 集成 `protectai/deberta-v3-base-prompt-injection-v2`（约 270MB，本地可跑）
   - 或先用远程 API（如火山引擎/OpenAI moderation）降级，保延迟 < 500ms
   - 关键：给融合决策加"置信度阈值可配"，让安全团队能调误报率

2. **容器化 + 配置化部署**（2-3 天）
   - 完善 Docker Compose（API + SQLite→可选 PG + 可选 Redis）
   - 环境变量全清单、`.env.example` 补全、启动脚本
   - 日志采集（结构化 JSON 日志 → 可选接 ELK/Loki）

3. **监控与健康**（2-3 天）
   - `/metrics`（Prometheus 格式）：请求量、拦截量、误报率、模型延迟
   - 存活/就绪探针、优雅关闭
   - 告警：拦截率异常飙升/骤降时通知

4. **安全自证**（2-3 天，安全产品不能自己有漏洞）
   - 威胁建模：管理端点鉴权、API key、注入防护
   - 依赖漏洞扫描、密钥不进镜像
   - 越权防护：审计/策略端点加鉴权

**验收**：容器化一键部署，能接真实模型，有监控指标，自身无高危漏洞。

### 阶段 2：合规能力（2-3 周，面向安全/合规团队的核心价值）

目标：让产品能对上企业审计/合规的要求。**这是区别于"技术 demo"的关键阶段。**

1. **审计报表与导出**（3-4 天）
   - 周期报表（日/周/月）：拦截量、命中规则 TOP、来源分布
   - 导出 CSV/PDF，支持按时间范围/会话/规则过滤
   - 关键：报表要能回答"过去 90 天谁被拦了、为什么、用了哪版策略"

2. **审计留存与完整性**（2-3 天）
   - 保留策略（`audit_retention_days` 已配置，需落地为定时清理）
   - 可选：审计日志哈希链（防篡改自证）——合规团队很看重这个
   - 导出可签名（可选）

3. **策略变更审批与台账**（3-4 天）
   - 现在热更新是"改了立刻生效"，合规团队要"变更可审批、可回滚、有记录"
   - 加一层：策略变更 proposal → 审批 → 生效 → 台账
   - 复用已有的 `policy_revision` 做版本台账

4. **合规映射文档**（1-2 天）
   - 出一份"本产品如何对应 X 合规要求"的映射（等保 2.0 / SOC2 / 企业内部安全规范）
   - 这是安全团队内部采纳时写报告必需的弹药

**验收**：能出一份"过去 90 天拦截审计报表"，策略变更有审批痕迹，有合规映射文档。

### 阶段 3：真实接入 + 推广（2-4 周，验证 + 扩散）

目标：从"我自己能跑"到"团队里别人用起来"。

1. **试点接入（1 周）**
   - 挑 1-2 个真实的内部 Agent（Claude Code 写代码 / 客服 Bot / 内部知识库问答）
   - 挂上 proxy，跑 1-2 周，收集：误报率、拦截真实攻击数、延迟影响
   - 这是"能不能推广"的生死数据

2. **调优（1 周，基于试点数据）**
   - 根据误报/漏报调规则阈值、补规则
   - 优化延迟（模型量化、缓存）

3. **内部推广（1 周）**
   - 面向团队做一次演示 + 写接入文档
   - 建一个"接入一个 Agent 只需改 base_url"的极简体验
   - 收集反馈 → 决定下一步（继续内部 → 或转开源/对外）

**验收**：至少 1 个真实 Agent 稳定接入 2 周，误报率在可接受范围，团队认可价值。

## 3. 时间与资源估算（单人）

| 阶段 | 周期 | 关键交付 | 风险 |
|---|---|---|---|
| 0 补齐 MVP | 1-2 天 | 完整产品 | 低（纯内部） |
| 1 工程化 | 1-2 周 | 可稳定部署 | 中（真实模型集成有坑） |
| 2 合规能力 | 2-3 周 | 报表+审批+台账 | 中（需求可能蔓延） |
| 3 真实接入 | 2-4 周 | 试点数据+推广 | 高（依赖真实 Agent 环境） |

**总计：6-10 周（约 1.5-2.5 个月）**，单人全职。

**可以砍的部分**（如果时间紧）：
- 审计哈希链、导出签名 → 砍掉（阶段 2 的可选项）
- Prometheus 监控 → 先做最小版（拦截计数即可）
- 真实模型 → 先用远程 API 顶着，不本地部署

---

## 4. 最关键的风险与前置决策

### 风险 1：真实判别模型的误报率（最大不确定项）
mock 模型永远 100% 听话，但真实模型会有误报。**误报率直接决定安全团队用不用。**
→ 需要阶段 1 尽早换真实模型，用 E1 的 30+ 样例实测误报/漏报。

### 风险 2：单人带宽
合规能力（阶段 2）最容易需求蔓延（"再支持个 XX 报表"）。单人必须守住 MVP 边界。

### 风险 3：真实 Agent 接入的环境依赖
E2/阶段 3 需要真实的 Agent + API key，这个不在代码控制内。

## 5. 需要你拍板的 3 个问题

在开始阶段 1 之前，有 3 件事需要你确认，因为它们决定路线怎么走：

1. **真实判别模型怎么接？**
   - (A) 本地跑开源模型（deberta-v3，~270MB，需要能下载 HF 模型的网络 + 一定内存）
   - (B) 先用远程 moderation API（更快，但依赖外部服务 + 有调用成本）
   - (C) 暂不换，继续 mock（先做工程化，模型后补）

2. **部署目标环境是什么？**
   - 内部是 Linux 服务器 / Docker 集群，还是就本机 Windows 跑着？
   - 这决定阶段 1 容器化做到什么程度

3. **有没有"必须对上的"合规标准？**
   - 比如你们内部有没有明确的等保 2.0 / SOC2 / 数据安全法要求？
   - 有的话阶段 2 的报表字段和留存策略我按它来设计，没有的话我给一套通用模板
