# 集团推广方案 · 桌面透明代理（手段②）

> 目标：让 AgentSoc 在「90% Windows 终端 + 工具五花八门」的集团环境中，以终端零改动的方式全覆盖接入。
> 文档日期：2026-09-17

---

## 一、问题定义

### 现状（已确认）
- 集团终端 90%+ 是 Windows
- 每个员工用的 AI 工具/脚本**各不相同**（Cursor、Claude Code、自研脚本、客服 Bot 等）
- 流量构成：**80% 直连公网官方**（api.openai.com / api.anthropic.com），**20% 已走内网模型网关**

### 核心矛盾
「改每个终端的 base_url」在试点（1-2 台）可行，但推广到全集团**不可行**——无法让每个员工去改每个工具的配置。

### 解决方向
把 AgentSoc 从「每个终端手动指向的代理」升级为「**集中部署的透明网关**」，让流量在网络层自动汇聚，终端零感知。

---

## 二、技术方案（选型已拍板）

| 决策项 | 选择 | 理由 |
|---|---|---|
| 方案 | 手段② 桌面透明代理 | 覆盖 80% 直连公网官方的流量 |
| 技术栈 | Go | 单文件 exe、无依赖、启动快、适合分发到 90% Windows |
| 分发 | 集团域控 / 软件分发系统 | 静默下发 + 统一配置 |

### 透明代理完整链路（四步，缺一不可）

```
客户端 ──> api.openai.com ──(hosts 劫持)──> 127.0.0.1:443 ──> 本地代理 ──> 集团 AgentSoc 网关
```

1. **改 hosts**：把 `api.openai.com`、`api.anthropic.com` 等解析到 `127.0.0.1`
2. **监听 443**：本地代理监听本机 443（需管理员权限）
3. **自签根证书**：生成自签 CA，装进系统「受信任的根证书颁发机构」（TLS MITM 解密）
4. **转发**：拦截到的请求转发到集团 AgentSoc 网关

> 参考实现：DevProxy、Ghosxy 等项目已验证此方案在 Windows 上可行。

---

## 三、分阶段落地（务实路线）

### 阶段 1：显式代理模式（✅ 已完成 MVP，无合规风险）

- 本地起 OpenAI 兼容代理，工具把 base_url 指向 `http://127.0.0.1:8899`
- 不改 hosts、不发证书、不做 MITM，合规零风险
- **产出**：`desktop-proxy/` 目录（Go 代码，可编译单文件 exe）
- **用途**：先验证「多工具接入 AgentSoc」的核心价值，作为说服集团安全/合规团队的 demo

### 阶段 2：透明代理模式（需合规授权）

- 在阶段 1 基础上，加「改 hosts + 自签证书 + 监听 443」
- 终端真正零改动，工具照常配官方地址
- **前置**：拿到集团安全/合规团队对「TLS MITM 解密」的书面授权

### 阶段 3：集团分发

- 打包单文件 exe + 静默安装 + 注册 Windows 服务自启
- 统一配置中心下发 `config.json`（上游地址、端口、按部门策略）

---

## 四、合规风险（重要，必须正视）

透明代理的本质是 **TLS 中间人（MITM）**，会解密终端上所有发往 OpenAI/Anthropic 的 HTTPS 流量。

| 风险 | 说明 | 应对 |
|---|---|---|
| 隐私合规 | 流量可能含员工个人数据（个人 ChatGPT 账号等） | 需明确授权 + 脱敏 + 告知；按《数据安全法》《个人信息保护法》规范 |
| 证书信任 | 下发 MITM 证书到全集团，安全团队常谨慎/拒绝 | 提前沟通，说明「仅拦截 AI 域名」+「只做检测不存储明文」 |
| 证书校验 | 部分客户端 cert pinning 会导致拦截失败 | 白名单机制，失败的客户端走显式代理兜底 |
| 端口冲突 | 443 可能被其他程序占用 | 检测冲突并提示 |

**结论**：透明代理（阶段 2）必须先过合规，用阶段 1 的显式代理 demo 去申请授权。

---

## 五、服务端需补齐的能力（配合终端代理）

无论显式还是透明，AgentSoc 服务端都要补「多协议适配」：

- 当前已支持：OpenAI 兼容 `/v1/chat/completions`
- **需补**：Anthropic 协议 `/v1/messages`（覆盖 Claude Code 等）
- 后续：多租户隔离、按部门策略、高可用
